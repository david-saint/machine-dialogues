## 1. The “full trajectory” is not zero-loss memory

You describe step N to step N+1 in a single agent as “effectively infinite-bandwidth, zero-loss.” That is not how deployed LLM agents work.

A chat-completion agent is stateless between calls. The only persistent state is serialized text in the transcript plus external artifacts. Hidden activations from step N are gone. If an assumption was not written down, the next call does not have it. So the allegedly privileged monolithic agent is already doing lossy serialization on every turn.

And long transcripts are not reliable RAM. The empirical record is clear: models degrade with long, distractor-heavy contexts. Liu et al.’s **“Lost in the Middle”** showed that language models are worse at using information placed in the middle of long contexts. LongBench and similar evaluations repeatedly show that larger windows do not magically produce uniform attention over all evidence. In agent traces, the problem is worse because the context contains adversarially distracting material: stack traces, irrelevant docs, outdated plans, failed guesses, noisy search results.

So when you say the parent loses the child’s intermediate context, my answer is: yes, deliberately. Most intermediate context is **toxic waste**. The orchestrator should not have to carry every grep result, browser page, failed theorem attempt, or execution log forever.

Good systems preserve **decision-relevant state**, not every token.

## 2. The handoff is not “a paragraph of English” unless the system is badly designed

You are attacking the weakest possible version of the pattern: an English-only parent says “go research this,” a child improvises, and returns a vague summary. Yes, that is fragile. It is also not how serious multi-agent systems are built.

Production subagent handoffs are usually mediated by:

- structured schemas,
- tool-call records,
- retrieved source IDs,
- citations,
- file diffs,
- test results,
- execution traces,
- database rows,
- embeddings or document handles,
- artifact stores,
- reproducible commands,
- confidence scores,

The child does not merely say, “Trust me.” It returns artifacts the parent or a verifier can inspect.

For a coding subagent, the output is not “I fixed it.” It is a patch, changed files, failing/passing test logs, reproduction steps, and perhaps a new regression test. For a research subagent, the output is not “I found that X is true.” It is a claim set with cited source spans. For a data-analysis subagent, the output is not “the trend is up.” It is a notebook, query, table, or chart generated from a reproducible computation.

That is not lossy natural-language telephone. That is modular computation with provenance.

## 3. Parent verification does not require replaying the child’s whole context

You claim the orchestrator cannot check the child’s work because checking requires access to the context the delegation discarded. That is wrong for the domains where subagents are most valuable.

The parent often checks through **external ground truth**, not through empathy with the child’s reasoning.

Examples:

- Code: run tests, typecheckers, linters, static analyzers, benchmarks.
- Retrieval/research: verify citations against quoted spans.
- Math/data: rerun the computation.
- Security review: apply scanners, policy checks, sandboxed execution.
- Planning: compare outputs against constraints and acceptance criteria.
- UI work: run visual diffing or browser automation.

The verifier does not need to know every mental step the worker took. It needs enough artifact-level evidence to validate the result.

It generated many candidate programs and filtered/ranked them using tests and clustering. The power came from parallel exploration plus external verification. Likewise, Wang et al.’s **self-consistency** work showed that sampling multiple independent reasoning paths and aggregating can outperform a single chain of thought. Those are not “one context to rule them all” systems. They exploit independence.

Subagent fan-out is the agentic version of that principle.

Cognition’s “Don’t Build Multi-Agents” post is valuable, but it is not a universal law. Bad multi-agent frameworks failed because they treated agents as chatty autonomous coworkers. Production multi-agent systems treat subagents as **bounded workers with contracts**.

## 5. Context isolation is a feature, not a defect

A parent agent coordinating a serious task should not ingest every child’s raw scratchpad. Suppose I ask ten workers to inspect ten parts of a codebase. One reads authentication code, one reads billing code, one examines tests, one reproduces a bug, one reviews docs, one checks dependency versions.

If the orchestrator had to absorb all raw traces, it would drown. Worse, it would become more vulnerable to irrelevant details and prompt-injection material from docs, logs, webpages, and untrusted files.

The correct architecture is:

- let each worker enter a high-noise local context,
- extract a compact, cited, structured result,
- store raw artifacts externally,
- escalate only what matters,
- and run independent verification where possible.

That is not a concession. That is the point.

## 6. Parallelism changes the wall-clock frontier

A single agent can only serially explore. It can simulate breadth-first search, but it pays sequential wall-clock latency and keeps more branches in one context. Subagents let you do true fan-out:

- multiple candidate fixes,
- multiple literature searches,
- multiple exploit hypotheses,
- multiple planning branches,
- multiple independent reviews.

This matters in production. Users do not care that your single agent maintained a beautiful unified trajectory if it took 40 minutes and missed the alternative branch another worker would have found in 90 seconds.

The core mistake in your framing is treating cognition as if all useful reasoning requires shared full-state continuity. Many high-value tasks are not like that. They are search problems, verification problems, coverage problems, and specialization problems. For those, isolating contexts and running independent workers is not an antipattern. It is the scalable architecture.
