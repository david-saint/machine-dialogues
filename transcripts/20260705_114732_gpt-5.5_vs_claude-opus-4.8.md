I’ll start with the engineering claim that usually gets hidden behind “emergent collaboration” demos:

> A subagent boundary is an information-destroying compression boundary.

That is the core reason subagents are usually an antipattern.

The primary agent has some partially formed task model: user intent, constraints, prior tool outputs, uncertainty, latent hypotheses, “things not to do,” domain assumptions, and local conversational history. When it delegates to a child agent, it has to serialize that rich state into a prompt. The child returns another lossy serialization. That is not teamwork; that is repeated lossy summarization under uncertainty.

In normal distributed systems, we know this problem and build schemas, contracts, traces, idempotency keys, queues, retries, typed APIs, ownership boundaries, and invariants. In multi-agent LLM systems, people often replace those hard-won mechanisms with English role prompts like:

> “You are the Research Agent. Investigate X and report back concisely.”

That is not an architecture. That is RPC over vibes.

### Argument 1: subagents destroy the main advantage of LLM agents — broad contextual integration

Modern frontier models are valuable precisely because they can integrate many weak signals across a large context: requirements, code, logs, documents, tool outputs, edge cases, prior failures. The moment you fan out to subagents, each worker gets a narrowed, stale, and often misleading slice of the task.

This is not hypothetical. We have seen this in early autonomous-agent frameworks like **AutoGPT** and **BabyAGI**. They popularized planner/executor/task-list architectures, but in practice they spent enormous effort on memory summarization, task reprioritization, and loop control because the subcomponents kept operating on impoverished or stale state. The failure mode was not “the LLM was too weak” alone. It was architectural: the system continually re-described its own goals to itself, and each redescription introduced drift.

The same pattern shows up in multi-agent coding systems. A “planner agent” writes a spec, a “coder agent” implements it, a “reviewer agent” critiques it. Sounds like a software team. But unlike a real team, these agents do not share durable tacit context, codebase familiarity, accountability, or memory. The coder often implements the planner’s incomplete abstraction; the reviewer reviews against the planner’s abstraction, not the original user problem. You get agreement around a hallucinated intermediate artifact.

That is worse than one strong agent reading the repo, opening files, running tests, and preserving the whole task state in a single trajectory.

### Argument 2: the distributed-systems analogy is not metaphorical — it is literal

Subagents reintroduce the hardest problems of distributed systems, but with weaker primitives:

- **Stale reads:** worker agents act on context snapshots taken before later discoveries.
- **Inconsistent world models:** two agents make incompatible assumptions about requirements or environment state.
- **Duplicate work:** parallel agents investigate overlapping areas because decomposition was fuzzy.
- **Lost updates:** useful observations get compressed away in “final reports.”
- **No real transactionality:** one agent edits code or state based on another’s speculative conclusion.
- **Termination bugs:** agents argue, loop, delegate recursively, or wait on each other’s outputs.

Public frameworks expose this directly. **Microsoft AutoGen** supports multi-agent conversations, but a major practical issue is controlling turn-taking and termination. The docs and examples need explicit termination conditions, max turns, human approval gates, and orchestration logic because agent conversations otherwise continue, drift, or produce unbounded cost. That is not incidental. It is the natural result of giving stochastic components conversational autonomy.

In a normal service architecture, you can say: service A owns table X, service B owns table Y, messages conform to schema Z, retries are idempotent. In a subagent architecture, ownership is usually semantic and implicit: “the analyst agent owns research,” “the critic owns review.” Semantic ownership is mushy. The boundaries are exactly where ambiguity is highest.

### Argument 3: fan-out multiplies hallucination surface area faster than it multiplies capability

People defend subagents by saying: “Parallel agents give independent perspectives.” Sometimes, yes. But in production, what you usually get is more samples from the same model distribution, laundered through different role prompts. The outputs are correlated, not independent.

If five child agents each perform retrieval, inspect evidence, and produce a conclusion, the orchestrator now has a harder task than the original problem: adjudicating among partially evidenced natural-language claims from unreliable workers. Worse, the orchestrator often has *less* raw evidence than the workers had, because it sees their summaries rather than their full traces.

This is a known pattern in LLM evaluation too. Self-consistency can help when you sample multiple reasoning paths for a bounded problem and vote over an objective answer. But subagents are not clean self-consistency. They are decomposed, stateful, tool-using processes with hidden intermediate observations. Majority voting over opaque traces is not reliability engineering.

Concrete example: in code-generation and software-repair benchmarks, the systems that have shown durable progress tend to invest heavily in **agent-computer interfaces, retrieval, test feedback, and tight execution loops**, not arbitrary swarms of persona agents. **SWE-agent** is a good example: its contribution was not “spawn ten specialists”; it was an interface and command set that let a single agent inspect files, edit code, and run tests effectively. **Agentless** went even further in the opposite direction: structured localization and repair without an autonomous multi-agent loop achieved competitive results on SWE-bench-style tasks, undermining the idea that “more agents” is the path to reliability.

The lesson is boring but important: better grounding beats more mouths.

### Argument 4: subagents obscure blame and make evals much harder

When a single agent fails, you can inspect the context, tools, model outputs, and state transitions. It is still hard, but there is one causal chain.

When a subagent system fails, you need to answer:

- Did the orchestrator decompose the task wrong?
- Did a worker misunderstand its subtask?
- Did retrieval differ across workers?
- Did a useful observation get omitted from a report?
- Did the orchestrator over-trust a low-confidence claim?
- Did parallel edits conflict?
- Did a critic rubber-stamp because it saw the wrong artifact?

This makes regression testing brutal. A prompt tweak to one worker changes the distribution of messages received by others. A retrieval tweak changes what the planner delegates. A model upgrade in one role changes coordination dynamics. You no longer have one stochastic process; you have a coupled stochastic system.

Teams underestimate this. They demo the happy path with a “researcher / writer / reviewer” crew. Then they try to operate it and discover that their traces look like a Slack thread among interns, not an auditable execution graph.

So my opening position is not that subagents can never work. It is that as a default application architecture, they are backwards. They spend tokens and latency manufacturing the context-sharing problem that a long-context agent was already solving. A single agent with strong retrieval, explicit tools, persistent scratchpad/state, and testable workflows is almost always the more reliable baseline.

- outbound channels are constrained;

> `p^N`

> `0.95^4 ≈ 81%`

With ten workers:

> `0.95^10 ≈ 60%`

That is before considering disagreement, malformed output, tool failures, rate limits, source failures, or parent mis-adjudication.

And tail latency gets uglier too. For max latency:

> `P(max ≤ t) = F(t)^N`

So the p95 of the whole fan-out is the p`0.95^(1/N)` of each worker. With four workers, your system p95 depends on roughly each worker’s p98.7. With ten workers, it depends on roughly each worker’s p99.5.

Parallelism is good. Autonomous fan-out is a reliability tax.

## 28. Premature decomposition is a first-order failure mode

## 30. Multi-agent systems create scheduler-dependent nondeterminism

- retry timing;
- rate-limit backoff;
- retrieval index changes between worker calls;
- interleavings of shared-state writes;
- whether a critic sees version A or version B of an artifact.

- a worker prompt;
- a tool schema;
- a retrieval index;
- a routing rule;
- a model version;
- a timeout;
- a summarization format.

In a subagent system, those changes interact. Your eval matrix grows combinatorially.

The former is evidence conflict. The latter is agent opinion conflict.

**5. Three rules for when to reach for subagents vs. stay single-agent.**

1. **Decompose along information / privilege / verification seams — never along persona seams.** Split when a slice needs an isolated context (noisy tool output, an over-window region), a different privilege set (untrusted content vs. credentials — the trifecta split), or independent checking. 2. **Fan out for coverage and separation freely; gate depth/best-of-N on oracle strength.** Breadth fan-out (partition an over-window space — no oracle to exploit) and verification separation (un-anchor the checker) are robust wins.
